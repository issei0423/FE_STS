# FE_STS 本番公開前チェックリスト

> ⚠️ **インフラ前提の注意(2026-07-13追記)**: 本チェックリストは Oracle Cloud VM + Nginx + systemd + Let's Encrypt を前提としています。issue #17-#21(DEPLOY-01〜06)対応で作成した [`docs/08_render_deploy_env_vars.md`](08_render_deploy_env_vars.md) は Render + Cloudflare Pages + TiDB Cloud Serverless + Brevo を前提とした別案です。どちらの構成を採用するか未確定のため両方を残していますが、実際にデプロイする際はどちらか一方に決定し、不採用側のドキュメント・設定(`deploy/nginx`、`deploy/systemd` 等)は整理することを推奨します。

**目的:** FE_STS（基本情報勉強時間リアルタイム共有Webサイト）を、安全で沖縄みらいの全生徒がいつでも利用できるWebアプリケーションとして公開するために不足している要素の洗い出し。

**リポジトリ:** https://github.com/issei0423/FE_STS
**作成日:** 2026-07-11

## 🔴 公開前に必須（これがないと「安全」と言えない）

### 1. 学校側の正式な許可

技術より先にこれ。`@sankogakuen.jp` のメールアドレスで認証し、**生徒の本名を収集・保管する**システムを個人が運用する構図になっている。学校のドメインを認証基盤に使う以上、学校（少なくとも担任・学科）への相談と承認は必須。無許可では、どんなにコードが安全でも「安全なサービス」にはならない。

- [ ] 担任・学科への相談と承認
- [ ] プライバシーポリシーの作成・掲示
- [ ] 利用規約の作成・掲示

### 2. レート制限

ログイン・サインアップ・メール送信エンドポイントに試行回数制限がないと、ブルートフォース攻撃とメール爆撃（Brevoの無料枠を他人に焼き尽くされる）に無防備。

- [ ] Spring側での実装（bucket4j など）、最低でも Nginx の `limit_req`
- [ ] 対象: `/api/auth/login`, サインアップ, メール再送, heartbeat

### 3. リフレッシュトークンの失効機構

JWT運用で一番漏れやすい所。ログアウト時・パスワード変更時にリフレッシュトークンを無効化できる仕組み（DB管理 or ローテーション）がないと、トークンが漏れた場合に有効期限まで乗っ取られ放題。

- [ ] `AuthService` の現状実装を確認
- [ ] ログアウト時の失効、リフレッシュトークンローテーションの実装

### 4. シークレット管理の確認

JWT秘密鍵・DBパスワード・Brevo APIキーが `application.properties` にベタ書きでコミットされていないか。

- [ ] `git log` 全履歴を含めて確認
- [ ] 一度でもコミットしていた場合は該当キーをすべてローテーション
- [ ] 本番は環境変数または VM 上の外部設定ファイルで管理

### 5. セキュリティヘッダー

Nginx設定に以下を追加（数行で済む）:

- [ ] `Strict-Transport-Security`（HSTS）
- [ ] `X-Frame-Options: DENY`
- [ ] `Content-Security-Policy`
- [ ] `X-Content-Type-Options: nosniff`

## 🟠 「いつでも利用できる」ために必須

### 6. systemdサービス化

現状のセットアップ手順は `spring-boot:run` 止まり。SSHを切ると停止し、クラッシュ・VM再起動後に誰も気づかない。

- [ ] `Restart=always` を含む systemd ユニットの作成
- [ ] jar ビルド → systemd 起動のデプロイ手順を docs に追記

### 7. Oracle Free Tier の資源回収リスク

Always Free の A1 インスタンスは、アイドル判定（CPU使用率等が低い状態が続く）で**回収されることがある**。

- [ ] アカウントを PAYG（従量課金）にアップグレード（Free枠内なら課金されない）

### 8. DBバックアップ

VMが飛んだら全生徒の記録が消えるのが現状。

- [ ] mysqldump の日次 cron
- [ ] VM外への退避（OCI Object Storage の無料枠など）
- [ ] リストア手順の確認（バックアップは復元できて初めて意味がある）

### 9. 死活監視

落ちてから生徒に言われて気づくのでは遅い。

- [ ] UptimeRobot（無料）で HTTPS 監視 + 通知設定

### 10. 証明書の自動更新

Let's Encrypt は90日で失効する。切れると全員アクセス不能になる、可用性事故として一番ありがちなパターン。

- [ ] `certbot renew` の systemd timer / cron が有効か確認
- [ ] 更新後の Nginx reload まで自動化されているか確認

## 総評

ハートビート方式・JWT認証・本名の閲覧範囲制限といった**設計判断は既に妥当**。不足しているのはほぼ「運用」のレイヤー。

最優先は **1（学校の許可）** と **7（Free Tier の資源回収対策）**。コードの穴は後から直せるが、学校の許可なしの個人情報収集と、ある日突然消えるインフラは設計以前の問題。
