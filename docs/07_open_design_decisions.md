# 未決事項の方針決定（issue #7 対応）

issue #7「仕様検討: リアルタイム勉強時間計測・認証まわりの設計懸念」で挙げられた懸念のうち、
既存の設計ドキュメント（01〜06）でカバーされていなかった項目について方針を決定する。

本ドキュメントは**方針決定とドキュメント反映**を目的としており、記載内容の実装（ハートビートAPI、
アイドル検知ロジック等）自体は別途フォローアップのissue/PRで対応する。

## 1. セッション終了検知（懸念点3）

`beforeunload` イベント単体はスマホでの信頼性が低く、ブラウザ強制終了・回線切断等も検知できない。
以下の方式を採用する。

- クライアントは計測中、一定間隔（例: 30秒ごと）でハートビート（`POST /api/study-sessions/heartbeat` 等）をサーバーに送信する。
- サーバー側は最終ハートビート時刻を記録し、一定時間（例: 90秒）ハートビートが届かない場合はセッションを自動終了（`endedAt` を最終ハートビート時刻で確定）とみなす。
- `beforeunload`/`visibilitychange` イベントも補助的に利用し、明示的にタブを閉じた場合は即座に終了リクエストを送る（ベストエフォート）。
- README懸念点にあるChromeのバックグラウンドタブ挙動変更の影響も、ハートビート＋サーバー側タイムアウト方式であれば緩和される。

## 2. 不正計測（放置）対策（懸念点4）

- クライアント側でユーザー操作（マウス/キーボード/タッチ）が一定時間（例: 10分）無い場合、アイドルとみなし計測を自動停止する。
- 1セッションあたりの上限時間（例: 8時間）を設け、超過分は計測しない。
- 上記はいずれもクライアント側の検知に加え、サーバー側でも異常に長いセッション（ハートビート途絶にもかかわらず継続扱いになっているもの等）を定期バッチでクリーンアップする。

## 3. 本名登録の運用方針（懸念点5）

- 本名データの閲覧範囲は管理者のみとする。生徒間では表示名（本名またはニックネーム選択制）のみを共有する運用とする。
- 卒業後、一定期間（例: 卒業年度末から6ヶ月）を経過したアカウントの本名・メールアドレス等の個人情報は削除またはハッシュ化する。
- 管理者による本名確認は目視ベースの運用を継続するが、サインアップ時のガイダンス文言で実名登録の必須性を明示する（既存の `docs/03_email_verification_flow.md` のサインアップフローに準拠）。

## 4. 認証方式の見直し（懸念点6・実装済み）

READMEに記載されていた「ログイン毎にメールでワンタイムパスワードを送付する」方式は、実装段階で
**サインアップ時のみメール確認リンクを送付し、以降はJWT（アクセストークン+リフレッシュトークン）でセッションを維持する**方式に変更済み。
詳細は [03_email_verification_flow.md](03_email_verification_flow.md) および `backend/src/main/java/com/fests/service/AuthService.java` を参照。
毎回のログイン負荷を軽減しつつ、`@sankogakuen.jp` ドメイン検証・メール確認という要件は維持している。

## 5. スマホ対応方針（懸念点7）

- レスポンシブ対応を必須要件とする。ブレークポイントは 768px（タブレット/スマホ境界）を基準とする。
- 過去問道場等、スマホ利用が主となる導線を優先してモバイルレイアウトを検証する。
- 対応状況はフロントエンド実装（`FE_STS` フロントエンドの `src/`）のCSS設計に順次反映する。

## 6. JWTアクセストークンの保存方式とXSS時の被害範囲（issue #16対応）

`src/App.tsx` の実装（`readStoredToken` / `persistToken`）を確認し、以下の運用を正式な方針として明文化する。

- 認証方式は「Authorization ヘッダ + CSRF対策無効・ステートレスJWT」を採用しており、この前提を維持する（httpOnly Cookie方式はCSRF対策とセットで別途設計が必要になるため不採用）。
- アクセストークンの保存先は、ログイン時の「ログインを記憶する」(`remember`)フラグで分岐する運用が既に実装されている:
  - `remember = true`: `localStorage`（キー `fe-sts:token`）にアクセストークンを保存し、次回訪問時に自動復元する。
  - `remember = false`: `localStorage` には保存せず、React state（メモリ）のみで保持する。タブを閉じる/リロードすると再ログインが必要になる。
  - メール確認リンク経由のログイン（`?token=...` → `/api/auth/verify`）は現状 `remember` の選択肢が無いため、常に `localStorage` に保存する（サインアップ直後の初回ログインとして扱う）。
- `dangerouslySetInnerHTML` 等の未サニタイズなHTML挿入箇所は本ドキュメント作成時点で確認されていない（Reactのデフォルトエスケープに依存）。
- **既知のギャップ**: バックエンドはリフレッシュトークンを発行・レスポンスに含める（`LoginResponse.refreshToken`）が、現時点でフロントエンド（`src/api/client.ts` の `LoginResponse` 型・`src/App.tsx`）はこれを一切保存・利用していない。そのためアクセストークン失効（既定1時間）後は自動更新されず再ログインが必要になる。この点はフロントエンド側の別issueとして切り出す。
- **被害範囲の評価**: 上記ギャップにより実質的にリフレッシュトークンはまだ被害範囲の緩和に寄与していないが、アクセストークン自体が短命（既定1時間）であるため、XSSでの窃取被害はその残存有効期間内に限定される。`remember=false` を選んだ場合は再読み込みで即座に無効化される点も踏まえ、本名等の個人情報を扱う点を考慮しても現行方式は許容範囲と判断し継続する。フロントエンドのリフレッシュトークン対応が完了すればアクセストークンの寿命をさらに短縮でき、被害範囲はより縮小する。
